03 — Technical case study

Making agent runs survive real-world failure

More case studies

[Case study 2 — title] [Case study 3 — title]

Problem

A customer-facing workflow is a sequence of steps — read a request, look up records, call an LLM, write to a CRM, send an email. Any step can fail, time out, or return something unexpected. The product needed every run either to finish correctly or to stop in a state a human could understand and resume.

Constraints

A small team, an existing Rails codebase, third-party APIs with rate limits and partial outages, LLM calls that are slow and non-deterministic, and strict expectations that a side effect (an email, a CRM update) never happens twice.

Options considered

A — In-process chains

Run each workflow as a single long job. Simple to write; state lives in memory, so a crash or timeout loses the run and retries repeat side effects.

B — Workflow engine

Adopt a dedicated durable-execution engine. Strong guarantees, but a new runtime to operate and a large conceptual jump for a small team on a tight timeline.

C — Durable state machine · chosen

Persist run state and an event log in PostgreSQL; execute each step as an idempotent Sidekiq job. Uses the stack the team already operates and gives most of B's guarantees.

Decision

Option C. The guarantees the product needed — durability, safe retries, resumability — come from data-model discipline, not from a new runtime. Keeping to PostgreSQL and Sidekiq meant one fewer system to operate and every engineer could reason about a run by reading a table.

Trade-offs

Deliberately gave up the built-in tooling of a workflow engine (visual timelines, versioned workflow code) and accepted writing our own step-scheduling and timeout logic. Throughput ceilings of a single Postgres write path were accepted as acceptable for the product's scale.

Implementation

Idempotency keys on every external call, stored with the step, so a retried job can detect a completed side effect and skip it.

Per-tenant queues with backpressure so one noisy customer cannot starve the rest; Redis-backed rate limits per external provider.

Replayable event log per run, which became the debugging tool for support and the basis for resuming a stalled run by hand.

What it changed for the team

New workflow types became a matter of defining steps, not re-solving reliability. Support could read a run's log instead of paging an engineer.
